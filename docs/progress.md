# 从一次升级推送到 ANC 实验

这次研究从 vivo TWS 3e 的一条更新提示开始：

> v2.6.3，1.08 MB。优化耳机连接双设备时的播放体验，优化系统稳定性。

关心的问题很具体：更新到底改了什么，会不会削弱降噪？随后又多了一个想法：如果能找到降噪参数，能否自己调整，让室内低频嗡声压得更好？

## 保存升级请求和官方原包

先从 App 的网络记录中保存升级信息和下载文件。原包大小为 1,079,790 字节，项目为 DPD2321A，芯片信息为 best1306。

为了做版本对比，还查过升级请求的 URL、App 日志和手机缓存，希望从中找到旧版。手机上的 App 是新装的，缓存线索没有留下旧包，这一阶段得到的是 v2.6.3。旧版本的收集继续保留为后续线索，研究转向手头文件及其他型号的多版本样本。

原包从此作为基线保存。后面的每份修改包都由这份原包重新生成，文件哈希用来区分原版、倍率和构建结果。

## 先看其他型号的升级改了什么

随后收到 TWS3、TWS3 Pro、TWS4 的多份固件，TWS4 又补充了更多历史版本。最终比较了 12 份 QCC 固件，对应九次相邻升级。

最初从包内文件和 ANC 静态参数入手。每份解析出十组配置，每组 212 个命名字段。同型号相邻版本的这些 ANC 参数保持一致，但一些程序模块已经变化。于是继续拆模块、反汇编主程序，追踪变化字段的使用位置。

逐步查到了这些内容：

| 版本变化 | 追到的实现 |
|---|---|
| TWS3 2.12.2 → 2.12.6 | ANC 管理器调整小值增益恢复、过渡和状态记录 |
| TWS3 Pro 3.8.6 → 3.9.7 | 音乐处理链后级增益预设从约 +12 dB 改为 +9 dB；贴合检测结果增加请求状态判断 |
| TWS4 多次升级 | 语音模块、DSP 时钟申请及其他音频处理变化 |
| TWS4 2.58.3 → 2.58.5 | ANC 初始化、贴合检测、工作缓冲及底层音量和数据衔接处理变化 |

这一步让分析从“某个数字变了”走到“数字被哪条路径使用”。例如 TWS4 中出现的 7、8 最终追到 DSP 时钟档位；Pro 的 −3 dB 则对应音乐链后级补偿。后续的参数判断都沿用了这种追调用、查配置、再核对实际数据的方式。

## 拆开 3e 的固件

3e 的包头是 `oviV`。顺着长度和边界拆开后，得到十段 LZMA，解压后拼成 1,857,368 字节的镜像。其中前九段各解压 192 KiB，最后一段解压 87,896 字节。

外层头中几项数据起初用途不明。将它们与每 64 KiB 的累计 CRC 对照，发现前 17 项是累计 CRC，最后一项是前面各项的累加和。镜像里另有 `CRC32_OF_IMAGE` 文本，包含内部 CRC。

接着做无修改重建：解开、原样装回，再与官方包逐字节比较。结果完全相同，重打包流程有了基准。之后改参数时，保留前九段压缩数据，只重压包含参数和内部 CRC 的第十段。

## 找到增益，也弄清了 512

ANC 配置里出现过 512。这个数参与 Q9 定点增益表示，换算后是 1.0。真正有用的线索来自增益合成和设置函数：它会把前馈增益乘以另一个浮点比例。

顺着指令引用，找到 RAM `0x20007b14`，再通过启动数据复制对应到镜像 `0x1c3e20`，初值为 `1.0`。

为了确定它的身份，又找到同芯片 BEST1306 SDK 的编译对象。对象中保留了 `anc_set_gain`、`anc_set_gain_f32` 和 `g_ff_adaptive_gain` 等符号。两个滤波复制函数与 vivo 机器码逐字节相同，增益函数在处理链接重定位后匹配，数据引用也一一对应。至此，这个浮点量被确认为前馈 ANC 自适应增益。

把原始机器码放进 Unicorn 执行后，输入增益和浮点比例的乘法结果也吻合。例如输入 512：0.50 倍得到 256，1.25 倍得到 640，1.50 倍得到 768；反馈通路在这些测试中保持 512。

## 从离线片段做到完整固件

早期做过两类原型：直接调整增益，以及在原有七节滤波器之后追加一节低频滤波。后者还涉及外部配置加载、工作缓冲和代码装载位置，研究内容更多。

实际刷写先选择了更容易对照的做法：在原位置修改前馈比例初值，保留现有程序和系数。构建器更新内部 CRC，再压缩第十段、更新包头长度和 CRC 表。每个包都检查完整镜像差异、独立解压和原始验包函数。

为检查工具是否真能发现错误，还做了几类反例：翻转载荷的一位、改坏魔数、制造超出容量的镜像长度，以及破坏 LZMA 属性后重新计算外层 CRC。最后一个反例尤其有用：外层检查可以通过，实际解压却失败，所以解压核对成为构建流程的一步。

## 找到本地安装入口

安装路线先考虑过拦截官方请求、替换下载文件，以及自己写 PC 更新器。分析官方 App 后，已经整理出升级消息、续传和提交阶段，PC 工具停在了离线协议原型。

后来资料中出现了 `vivotws_local_FW.apk`。反编译后，找到了固定的 `/sdcard/vivotws/update.bin` 文件入口。它还把更新信息中的目标版本设为 `2147483647`，让 App 发起更新，并跳过一层原有的文件 MD5 比较。

这样，已有的 App 蓝牙升级流程可以直接读取本地包，安装步骤也简化成：准备 BIN、放到指定路径、重启 App、进入固件更新。

## 实机对照按什么顺序进行

最先安装的是 1.01 倍。实验者反馈刷入后没有变砖，完整修改包走通了安装尝试。

因为 1% 的变化很难判断听感，接着制作了 0.50 倍对照。刷入后的反馈是：降噪明显减弱。这使前馈比例的作用从代码和模拟计算，进一步对应到了实机听感。

随后制作了 1.50 倍和 1.25 倍，供后续比较。各份包的记录如下：

| 倍率 | 用途与进展 |
|---|---|
| 1.00 | 中性重建，与官方原包逐字节相同 |
| 0.99 | 离线反向对照 |
| 1.01 | 已刷入，反馈没有变砖 |
| 0.50 | 已刷入，反馈降噪明显减弱 |
| 1.50 | 已制作，等待听感与运行记录 |
| 1.25 | 已制作，等待听感与运行记录 |

听感来自本次实验者的反馈。后续读者可以用同一噪声源、佩戴方式和降噪模式重复比较，补充左右耳差异、底噪和低频变化。

## 回看官方日志，再整理成工具

双设备部分还追到了播放状态、切换请求防重复、设备有效性和目标一致性检查，并执行了相关原始指令。它们与官方描述的双设备播放场景相符；旧版 3e 样本将用于进一步找出本次具体改动。系统部分则找到了控制器异常检查和崩溃记录。

最后，把散落在研究目录里的解包、制作和校验脚本整理成独立命令：`inspect`、`unpack`、`build`、`verify`。六份构建结果与早期产物逐字节一致，配套保留了七项测试和反例检查。
