# 耳机固件怎么拆，参数怎么找

研究其他型号时，可以沿用这次的顺序：保存原包，识别格式，拆容器和分区，定位功能，再把修改装回完整包。

## 从升级请求和文件头开始

先保存 App 返回的版本、更新日志、文件长度和下载记录，为原包计算哈希。再查看文件开头、芯片字符串、项目名和构建信息，把样本按格式分类。

手头的 vivo 样本有两条路线：

| 样本 | 文件头 | 接下来的分析 |
|---|---|---|
| TWS 3e | `oviV` | 解析包头、LZMA 分段及 ARM 镜像 |
| TWS3、TWS3 Pro、TWS4 | `APPUHDR5` | 拆分区与文件系统，提取下载模块和 PS 参数 |

本地固件 App 的资料介绍了 TWS5 之前产品的刷写入口。文件头检查补上了另一层分类：同系列可以共享寻找入口的思路，具体解包再按拿到的格式展开。

## 3e 的包头和 CRC 表

3e 外层包头为 512 字节，镜像运行地址按 `0x2c010000 + 镜像偏移` 换算。完整 BIN 的文件偏移与解压镜像偏移分别记录。

| 完整 BIN 的位置 | 含义 |
|---|---|
| `0x00` | `oviV` 魔数 |
| `0x04` | 压缩载荷长度，小端 uint32 |
| `0x08` | 完整载荷 CRC32 |
| `0x10` | 项目标识字段，本包为 2321 |
| `0x18 / 0x1c` | 目标偏移字段，本包均为 `0x10000` |
| `0x20 / 0x24` | 解压镜像长度与 CRC32 |
| `0x2e` | CRC 表项数，小端 uint16，原包为 18 |
| `0x30` 起 | 每 64 KiB 的累计 CRC，最后一项保存前面各项的 uint32 累加和 |

这张表是通过实际计算找到的：分别计算前 64 KiB、128 KiB，直到整个载荷，再与头中的数值逐项比较。原包 `0x70` 恰好保存整载荷 CRC，`0x74` 保存累加和。实现时按表项数量定位末项，表长变化也能继续处理。

## 解压十段 LZMA

`0x200` 开始是四个 `FF`，后续每段由“大端 uint32 压缩长度 + LZMA FORMAT_ALONE 数据”组成。原包十段拼成 1,857,368 字节镜像，前九段各为 192 KiB，末段为 87,896 字节。

镜像内 `CRC32_OF_IMAGE=0x` 后的八字符保存内部 CRC，计算范围止于数字文本起点。本包起点为 `0x1c5700`。外层末尾还有同名文本，当前重打包保留其原字节，后续继续追踪读取位置。

重建按依赖顺序进行：修改镜像，更新内部 CRC，重新压缩变化的块，再更新镜像 CRC、载荷长度和累计 CRC 表。先做无修改重建，与原包逐字节比较；这个基准通过后，再制作参数实验。

一个参数会改变很多压缩字节，因此比较分两层做：完整包检查包头和压缩块，解压后检查实际参数与程序。型号、版本和暂未命名的头字段也参加逐字节比较。

## 用 SDK 和原始指令确认增益字段

在 3e 中，镜像 `0x1c3e20` 的 float32 初值为 `1.0`。启动复制后，它落在 RAM `0x20007b14`，增益函数从这里读取比例并与前馈整数增益相乘。

确认用途用到了同芯片 SDK 的编译对象：

| SDK 符号 | vivo 镜像偏移 | 对照结果 |
|---|---|---|
| `iir_coef_copy` | `0x3fa30` | 28 字节完全相同 |
| `iir_filter_coef_copy` | `0x3fe2c` | 116 字节完全相同 |
| `anc_set_gain` | `0x4122c` | 处理链接重定位后，152 字节匹配；数据引用对应 `g_ff_adaptive_gain` |
| `anc_set_gain_f32` | `0x41300` | 处理重定位后，26 字节匹配；实际跳转到上述整数函数 |

SDK 的函数名、数据符号、重定位关系，加上产品指令实际使用的位置，共同给出了字段身份。配置中的 512 和移位 9 对应 Q9 格式，增益分析继续追到乘法和写入结果。

参考 SDK 的 `anc_set_gain2_float` 会把赋值限制在 0～1。vivo 中对应的运行时赋值路径仍在追踪，启动初值、后续更新和硬件增益分别是可以继续核对的位置。

## 让原来的校验函数再检查一遍

Python 负责解析和重打包，7-Zip 独立解压每一段。然后从原镜像取出以下函数，放进 Unicorn 执行：

| 镜像偏移 | 检查内容 |
|---|---|
| `0x12c974` | 原始 CRC32，核对已知向量、累计载荷、整镜像和内部 CRC |
| `0x1559f0 / 0x155bf4` | 原始应用验包函数，在模拟 RAM 和 Flash 中读取候选包 |
| `0x4122c` | 原始增益设置函数，加载候选启动数据，检查六种输入、重复设置和反馈对照 |

执行环境拦截日志、存储和外部回调，硬件输出通道设为零。应用验包函数里的 CRC 回调使用 zlib，另一项检查则执行原始 CRC 指令，两路结果对照。

反例包括破坏载荷、魔数、长度和 LZMA 属性。曾经有一个内存样本，在修复外层 CRC 后通过了应用验包，但解压失败。这个结果说明了为什么需要把多个检查串起来，也让解压对照成为每次构建的固定步骤。

## 比较其他型号时继续追用途

TWS3、TWS3 Pro 和 TWS4 的静态 ANC 配置结构相近，实际系数不同。跨版本比较时，将参数变化与代码变化分开，再追参数选择、模式切换、增益恢复及配置加载路径。

Pro 的一个预设增益下降，后来通过实际注册的处理链、算子角色和 UCID 消息，确认落在音乐链末端。TWS4 的 7、8 则通过接口和调用链对应到 DSP 时钟档位。这类核对能让“改了哪里”继续回答“改的东西用在哪里”。

## 从 SDK 继续追启动与恢复

SDK 的压缩复制代码提供了函数和结构线索。对照 vivo 后发现，SDK 样本读取 32 字节启动信息，vivo 已追到的路径写入 104 字节；解压块尺寸也不同。

这些差异可用来继续识别产品实现：从提交函数保存的数据出发，寻找重启后的读取方，再核对解压、验签、替换和失败处理。当前的研究问题整理在[下一步](boundaries.md)。
