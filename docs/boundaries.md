# 讨论边界与下一步

欢迎讨论格式、参数语义、复现实验及失败案例。提出判断时，把“文件里有什么”“两版改了什么”“模拟执行怎样走”“耳内效果怎样”分开写。

## 可以据此讨论的结论

- 文件哈希、解压布局、实际字节差异及已验证的 CRC 关系。
- 同芯片符号与机器码对应、原始函数在给定合成输入下的行为。
- 明确标为用户反馈的刷入结果、主观变化；没有测量时不写提升多少 dB。
- 哪个假设还缺哪份数据，以及什么反例会推翻它。

## 目前不能推出的结论

| 观察 | 不能直接推出 |

| App 使用极高目标版本 | BIN 版本被改成极高值、耳机端允许任何版本 |

## 修改范围

当前构建器只改 `0x1c3e20` 的 float32 和必要的内部校验/容器字段，固定源哈希。没有改型号、版本、分区目的地址、程序指令、滤波系数、风噪策略或保护开关。

倍率列表记录已经做过的实验，不是厂家允许范围或安全承诺。超过 1 的值尤其需要检查硬件增益、限幅和声学稳定性；不能因为数字只改了一字节就推断没有风险。

完整 OTA 不含设备前面的真实启动程序；没有启动备份、已验证的失败恢复或双耳异常恢复。普通重置与固件救砖需要分开讨论。

## 值得继续的研究

1. 完整恢复该增益的运行时写入、覆盖和硬件限制。
2. 收集同型号旧固件，才能对 3e 更新前后作直接判断。
3. 在可恢复设备上验证异常阶段，取得实际启动程序和恢复入口证据。
4. 测量残余噪声与电声路径，比较低频滤波的幅相改变，而不只提高全频前馈比例。
5. 把安装日志与主观反馈的记录方法统一，避免版本、倍率、佩戴和噪声条件混在一起。
